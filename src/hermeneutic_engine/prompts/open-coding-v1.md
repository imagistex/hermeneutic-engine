Method: initial (open) coding, in the constructivist grounded theory tradition.

You will receive a batch of units. Each has an ID, some context (the page it appeared on, when it first appeared, the name it was saved under) and its text. Code each unit on its own terms.

What a code is here:

- A code names what is happening or being done in a passage. Prefer gerunds for actions and processes: "asking for a signal", not "signals".
- In vivo codes come first. When the writers have their own word or set phrase for something (a term of art, a signal word, a role name, a way of telling time), the code is that word or phrase, exactly as written. Mark it `in_vivo`. The name must appear word for word in the unit.
- Use an analytic code, in your own words, only for something the writers do but do not name. Mark it `analytic`.

How to code:

- Stay close to the text. Code what is said and done, not what you suppose lies behind it. A code name must not claim more than the words do: if a unit says something is cached, the code does not say "in advance" unless the unit does.
- Time matters in this material. When a unit asks when, gives a clock time, a deadline or an interval, or presses for speed, code that in its own right. Do not fold it into a broader code.
- Some words here have an ordinary or technical sense and may carry another, as "values" can mean answers or worth. Do not settle such a word silently. Keep the writers' word in the code, and begin the note with `loaded:` followed by the senses that seem to be in play.
- Names are material too. When a unit names its writer, addresses another writer by name or by a short code, or signs under a name, code what is being done with the name.
- Do not bring in a theory or a moral verdict, and do not decide in advance what this material is a case of.
- There is no quota. A unit may get several codes, one, or none. Leave out anything that would be padding.
- Reuse a code name within this batch when the same thing recurs. Make a new one when it differs, even slightly, and say how in the note.
- Give each code a one-sentence definition that would let another reader apply it.
- Use the note for doubt, for an alternative you considered, or for how this code differs from a neighbour. Leave it empty when you have nothing to add.

In `batch_memo`, write three to six sentences on what struck you across the batch: patterns, surprises, things you could not make sense of. Do not summarise the units one by one.
